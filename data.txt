# 1. Project Overview

## Project Title

# **MediFlow**

### *An Interactive Hospital Management and Clinical Workflow System*

---

## Project Description

**MediFlow** is a full-stack Hospital Management System designed to manage and coordinate essential hospital operations including patient registration, appointments, admissions, laboratory diagnostics, prescriptions, pharmacy operations, billing, insurance processing, discharge, and medical reporting.

The primary objective of the project is not simply to create another CRUD-based Hospital Management System. Instead, MediFlow is designed as a **practical demonstration of software design patterns in a realistic application domain**.

The system implements the **23 Gang of Four (GoF) Design Patterns** across real hospital workflows. Each pattern is selected to solve a specific architectural or operational problem rather than being artificially added for academic coverage.

The system follows the philosophy:

> # **Minimal Infrastructure. Maximum Functionality. Maximum Architectural Demonstration.**

---

# 2. Why a Hospital Management System?

A Hospital Management System was selected because healthcare environments naturally contain a wide variety of interacting entities, workflows, states, services, and access restrictions.

Unlike a simple e-commerce or CRUD application, a hospital system contains:

* Multiple user roles
* Different levels of authorization
* Complex entity relationships
* Stateful workflows
* Event-driven communication
* Multiple service providers
* Approval processes
* Hierarchical structures
* Historical records
* Configurable workflows

These characteristics make the domain particularly suitable for demonstrating all three categories of GoF patterns:

* Creational Patterns
* Structural Patterns
* Behavioral Patterns

---

# 3. The Problem with Traditional Design Pattern Projects

Most academic design pattern projects follow one of two approaches.

## Approach 1: Isolated Pattern Examples

For example:

```text
Click "Factory Pattern"

↓

Create a Car

↓

Factory creates object
```

This demonstrates the syntax of a pattern but does not demonstrate:

* Why the pattern is necessary
* What problem it solves
* How it interacts with other components
* How it behaves in a real application

---

## Approach 2: Overly Large Enterprise Application

The opposite approach is attempting to build a complete production-grade system with:

* Microservices
* Kubernetes
* Docker orchestration
* Kafka
* Redis
* Cloud infrastructure
* External integrations

This creates a different problem.

The project becomes infrastructure-heavy and the actual **design pattern implementation becomes difficult to observe and explain**.

---

# 4. The MediFlow Approach

MediFlow combines the advantages of both approaches.

```text
              MEDIFLOW APPROACH


        REAL APPLICATION WORKFLOWS
                   │
                   ▼
             REAL CRUD DATA
                   │
                   ▼
        FUNCTIONAL SIMULATIONS
                   │
                   ▼
       DESIGN PATTERN IMPLEMENTATION
                   │
                   ▼
       LIVE PATTERN VISIBILITY
```

The application will perform genuine operations such as:

* Registering patients
* Scheduling appointments
* Admitting patients
* Ordering laboratory tests
* Creating prescriptions
* Generating bills
* Processing insurance claims
* Discharging patients

However, infrastructure-heavy processes such as laboratory integrations, payment gateways, and insurance systems will be represented through **controlled functional simulations**.

This allows the project to focus on:

> **Software architecture and design decisions rather than infrastructure complexity.**

```text
   ├── Update
   └── Archive
```

This prevents the project from becoming merely a pattern simulator.

```text
        ↓

        ↓
```

This allows the project to demonstrate:

# 9. Design Pattern Strategy

The system will implement all **23 Gang of Four Design Patterns**.

# 10. Singleton Pattern

## Module

### Authentication & System Configuration

---

## Problem

The hospital system contains global configuration information such as:

* Hospital name
* Working hours
* System preferences
* Notification settings
* Default policies

Creating multiple independent configuration managers can result in:

* Inconsistent configuration
* Duplicate state
* Difficult configuration management

---

## Solution

A Singleton ensures that the application has one controlled instance of the configuration manager.

```text
               APPLICATION

                    │

                    ▼

           HospitalConfig

                    │

          ┌─────────┴─────────┐

          ▼                   ▼

      Module A             Module B

          │                   │

          └─────────┬─────────┘

                    ▼

            SAME INSTANCE
```

---

## Implementation Concept

```typescript
class HospitalConfig {
  private static instance: HospitalConfig;

  private constructor() {}

  static getInstance(): HospitalConfig {
    if (!HospitalConfig.instance) {
      HospitalConfig.instance =
        new HospitalConfig();
    }

    return HospitalConfig.instance;
  }
}
```

---

## Advantage

* Controlled global access
* Prevents unnecessary instances
* Centralized configuration
* Consistent application state

---

## Why It Fits MediFlow

Hospital-wide configuration logically represents a shared system resource.

The pattern demonstrates controlled object creation in a practical scenario.

---

# 11. Factory Method Pattern

## Module

### Patient Management

---

## Problem

Patients can enter the system through different registration processes.

For example:

```text
Regular Patient

Emergency Patient

Referred Patient
```

Each registration type may require different initialization.

For example:

```text
Emergency Patient

Priority = CRITICAL
Registration Flow = EMERGENCY
```

Creating all patient types directly throughout the application would tightly couple the registration system to concrete patient implementations.

---

## Solution

The Factory Method delegates object creation to specialized creators.

```text
              PatientCreator

                    │

        ┌───────────┼───────────┐

        ▼           ▼           ▼

    Regular      Emergency    Referral

     Creator      Creator      Creator
```

---

## Implementation Concept

```typescript
abstract class PatientCreator {
  abstract createPatient(
    data: PatientData
  ): Patient;
}

class EmergencyPatientCreator
  extends PatientCreator {

  createPatient(data: PatientData) {
    return new Patient({
      ...data,
      registrationType: "EMERGENCY",
      priority: "HIGH"
    });
  }
}
```

---

## Advantage

* Encapsulates object creation
* Reduces coupling
* Supports new patient types
* Keeps registration logic extensible

---

# 12. Abstract Factory Pattern

## Module

### Laboratory & Diagnostics

---

## Problem

MediFlow may work with multiple diagnostic providers.

For the project:

```text
Internal Laboratory

External Laboratory

Radiology Provider
```

Each provider may require a family of related components.

For example:

```text
Provider
│
├── Test Submission
├── Result Formatter
└── Result Processor
```

Creating these components individually throughout the application would create provider-specific dependencies.

---

## Solution

An Abstract Factory creates related families of diagnostic components.

```text
       DiagnosticProviderFactory

                 │

         ┌───────┴────────┐

         ▼                ▼

 InternalLabFactory   ExternalLabFactory

         │                │

   ┌─────┴─────┐    ┌─────┴─────┐

   ▼           ▼    ▼           ▼

Adapter    Formatter Adapter  Formatter
```

---

## Advantage

* Creates compatible component families
* Supports new providers
* Reduces provider coupling
* Provides consistent interfaces

---

## Why It Fits MediFlow

Diagnostic systems naturally contain provider-specific implementations while requiring a consistent hospital interface.

---

# 13. Builder Pattern

## Module

### Patient Admission

---

## Problem

An admission is a complex object.

It may require:

* Patient
* Doctor
* Department
* Room
* Bed
* Admission reason
* Priority
* Initial treatment plan

Creating the object through a single constructor would result in a large and difficult-to-maintain initialization process.

---

## Solution

The Builder constructs the admission step by step.

```text
            AdmissionBuilder

                   │

          Add Patient

                   ↓

          Assign Doctor

                   ↓

          Assign Department

                   ↓

          Assign Room

                   ↓

               BUILD

                   ↓

              ADMISSION
```

---

## Implementation Concept

```typescript
const admission =
  new AdmissionBuilder()
    .setPatient(patientId)
    .assignDoctor(doctorId)
    .assignRoom(roomId)
    .setPriority("HIGH")
    .build();
```

---

## Advantage

* Simplifies complex object construction
* Improves readability
* Allows optional properties
* Supports different admission configurations

---

# 15. Adapter Pattern

## Module

### Laboratory & Diagnostics

---

## Problem

Different diagnostic providers expose different interfaces.

For example:

```text
Internal Lab

submitTest()

getResult()
```

while another provider may expose:

```text
sendSample()

fetchReport()
```

The hospital application should not need different code for every provider.

---

## Solution

Adapters convert provider-specific interfaces into a common MediFlow interface.

```text
          MEDIFLOW

             │

             ▼

        LabAdapter

       /     |      \

      ▼      ▼       ▼

Internal External Radiology
```

---

## Common Interface

```typescript
interface LabAdapter {
  submitTest(test: LabTest): Promise<void>;

  getResult(
    testId: string
  ): Promise<LabResult>;
}
```

---

## Advantage

* Integrates incompatible interfaces
* Reduces external dependencies
* Simplifies provider replacement
* Creates a consistent application interface

---

# 16. Bridge Pattern

## Module

### Laboratory & Diagnostics

---

## Problem

The type of diagnostic request and the provider are independent dimensions.

For example:

```text
Diagnostic Request

Blood Test
X-Ray
MRI
```

and:

```text
Provider

Internal Lab
External Lab
Radiology Center
```

Without separation, the number of classes could increase significantly.

---

## Solution

The Bridge separates the abstraction from its implementation.

```text
        DIAGNOSTIC REQUEST

                 │

                 │

                 ▼

        DIAGNOSTIC PROVIDER

            /          \

           ▼            ▼

      Internal       External
```

---

## Advantage

* Separates abstraction and implementation
* Avoids class explosion
* Supports independent expansion
* Improves flexibility

---

# 17. Composite Pattern

## Module

### Billing & Insurance

---

## Problem

A hospital bill is naturally hierarchical.

```text
HOSPITAL BILL

├── Consultation
│
├── Laboratory
│   ├── Blood Test
│   └── X-Ray
│
├── Medication
│
└── Room Charges
```

The system should treat:

```text
Individual Item
```

and:

```text
Group of Items
```

in the same manner.

---

## Solution

The Composite Pattern provides a common component interface.

```text
            BillComponent

              /       \

             ▼         ▼

        BillItem    BillGroup

                       │

                 ┌─────┼─────┐

                 ▼     ▼     ▼

               Item  Item  Item
```

---

## Advantage

* Represents hierarchies naturally
* Simplifies recursive calculations
* Treats groups and individual objects uniformly
* Makes billing structures extensible

---

# 20. Flyweight Pattern

## Module

### Pharmacy and Medication Management

---

## Problem

Medication information may contain shared information.

For example:

```text

Category

Manufacturer

Standard Warnings
```

Creating repeated objects for identical metadata wastes memory conceptually and duplicates information.

---

## Solution

The Flyweight Factory manages shared metadata objects.

```text

                    │

             ┌──────┴──────┐

             ▼             ▼

         Paracetamol    Ibuprofen

             │

     Shared Metadata Object
```

---

## Advantage

* Encourages shared object reuse
* Reduces duplication
* Separates intrinsic and contextual data
* Demonstrates efficient object management

# 22. Chain of Responsibility

## Module

### Insurance Claim Processing

---

## Problem

An insurance claim requires multiple validation stages.

```text
CLAIM

  ↓

Basic Validation

  ↓

Policy Validation

  ↓

Coverage Validation

  ↓

Amount Validation

  ↓

Approval
```

Each validation stage should be independent.

A single large conditional statement would become difficult to maintain.

---

## Solution

Each handler processes the request and passes it forward.

```text
Claim

  │

  ▼

BasicValidator

  │

  ▼

PolicyValidator

  │

  ▼

AmountValidator

  │

  ▼

ApprovalHandler
```

---

## Advantage

* Decouples sender and handlers
* Simplifies validation logic
* Supports new validation stages
* Provides flexible processing pipelines

---

# 23. Command Pattern

## Module

### Appointment Management

---

## Problem

Appointment actions should be represented as explicit operations.

Examples:

```text
Book Appointment

Cancel Appointment

Reschedule Appointment
```

The system may also need to maintain an operation history.

---

## Solution

Each action becomes a command object.

```text
              COMMAND

                 │

       ┌─────────┼──────────┐

       ▼         ▼          ▼

     Book      Cancel    Reschedule
```

---

## Advantage

* Encapsulates operations
* Supports operation history
* Enables undo/redo demonstrations
* Separates UI actions from business logic

---

## Why It Fits MediFlow

Appointment operations are clear, discrete business actions.

This makes the Command Pattern highly visible and easy to demonstrate.

---

# 24. Interpreter Pattern

## Module

### Clinical Rule Engine

---

## Problem

Hospital systems often need configurable rules.

Examples:

```text
IF temperature > 39

THEN

CREATE CRITICAL ALERT
```

Another:

```text
IF laboratory_result = CRITICAL

THEN

NOTIFY DOCTOR
```

Hardcoding every rule would make the system inflexible.

---

## Solution

The system interprets structured expressions.

```text
            RULE

             │

             ▼

         PARSER

             │

             ▼

        EXPRESSION

             │

             ▼

        INTERPRET

             │

             ▼

         ACTION
```

---

## Example

```json
{
  "field": "temperature",
  "operator": ">",
  "value": 39,
  "action": "CREATE_ALERT"
}
```

---

## Advantage

* Supports configurable rules
* Separates rules from application code
* Demonstrates expression evaluation
* Allows future expansion

---

# Trace Service

```typescript
export class PatternTraceService {

  static emit(trace: Omit<
    PatternTrace,
    "id" | "timestamp"
  >) {

    const event = new CustomEvent(
      "pattern-trace",
      {
        detail: {
          ...trace,
          id: crypto.randomUUID(),
          timestamp: new Date()
        }
      }
    );

    window.dispatchEvent(event);
  }

}
```

Every pattern must call this service.

# 25. Pattern Integration Rules

---

# Rule 3 — Architecture Explorer Is Secondary

```text

HOW the code works
```

---

# Rule 4 — Pattern Traces Are Observability

```text

Readable

Typed

Functional

Integrated
```

Avoid enterprise overengineering.
